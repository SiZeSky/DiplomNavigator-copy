## 4. Подтверждённое состояние данных

В ходе проверки подтверждено:

- `student_id=2` имеет завершённое закрепление за темой `id=1`;
- у закрепления темы `id=1`:
  - `status = completed`;
  - `current_stage = defended`;
  - `progress_percent = 100`;
- `student_id=1` имеет активное закрепление за темой `id=2`;
- тема `id=2` остаётся опубликованной;
- студент `student_id=3` относится к кафедре ПИ, но `GET /topics` возвращает
  пустой список;
- попытка подать заявку на тему `id=1` возвращает `409 Topic already has an assignment`.

## 5. Найденные расхождения backend-логики

### 5.1. Завершённая тема остаётся опубликованной

После перевода работы на этап `defended` закрепление становится
`completed`, но статус самой темы не меняется и остаётся `published`.
Поэтому научрук видит такую тему как «Открыта для заявок».

Фактическая защита от повторной заявки есть: сервис возвращает `409`, если
у темы уже существует незакреплённое или завершённое закрепление. Однако
статус темы и её отображение не согласованы.

### 5.2. Студент не видел занятые темы (исправлено)

Изначально `GET /topics` для студента исключал любую тему, у которой
существует `Assignment` со статусом, отличным от `cancelled`. После исправления:

- опубликованная тема с активным или завершённым закреплением отображается;
- ответ содержит `is_reserved: true` и `status_label: "Занята"`;
- новая заявка по такой теме отклоняется с HTTP 409.

Теперь список согласован с user flow: студент видит актуальное состояние темы,
а бизнес-правило повторного бронирования сохраняется.

### 5.3. Студент не видел прогресс работы (исправлено)

Добавлены `GET /works/me` и уведомления `assignment_progress_updated`.
Студент получает данные о текущем:

- `in_progress`;
- `under_review`;
- `admitted_to_defense`;
- `defended`.

Прогресс теперь доступен без supervisor-роли.

### 5.4. Workflow заявки на удаление темы (исправлено)

В user flow предусмотрен сценарий:

1. научрук создаёт заявку на удаление темы;
2. завкафедра рассматривает заявку;
3. завкафедра одобряет или отклоняет её;
4. при отклонении тема остаётся доступной;
5. при одобрении тема архивируется или удаляется по согласованному правилу.

Добавлены модель, миграции, endpoints и уведомления. При отклонении тема
остаётся без изменений, при одобрении переводится в архив с причиной `deleted`.

### 5.5. В seed не было отдельной роли завкафедры (исправлено)

Seed создаёт `seed.head.pi@example.com` и `seed.head.is@example.com` с ролью
`zavkaf`. Их пароль — значение `SEED_PASSWORD`; повторный seed существующие
пароли не меняет.

## 6. Исправления, внесённые после проверки

По итогам проверки реализованы:

- опубликованные занятые темы снова выдаются студенту с `is_reserved: true` и
  подписью `Занята`, но попытка заявки по-прежнему возвращает `409`;
- при переводе работы в `defended` тема переводится в `archived` с причиной
  `completed`;
- завершённая тема отображается как `В архиве (завершена)`;
- добавлен `GET /works/me` для просмотра студентом своих закреплений и
  прогресса;
- студент получает уведомление `assignment_progress_updated` при изменении
  этапа или процента работы;
- тесты обновлены под новый контракт занятых тем.

## 9. Итог

Основной backend MVP запускается и выполняет базовый сценарий:

```text
авторизация → опубликованная тема → заявка студента →
решение научрука → закрепление → прогресс → защита
```

Основной backend user flow теперь включает согласование удаления темы через
завкафедру. Остаётся отдельно завершить ручную проверку функций дашборда
завкафедры, нагрузки, лимитов и ручных назначений.
